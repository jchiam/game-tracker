## Why

P5X parties aren't freeform 4-slot teams. The real game structure is: Wonder (fixed main character, always present) equipped with up to 3 personas from a separate catalog of ~149, plus 3 thieves. The current 4-homogeneous-slot model cannot express this. Players need to track which personas they assign to Wonder per party, distinct from the thief selection.

## What Changes

- New data catalog: `src/data/persona-5-phantom-x/personas.ts` (~149 equippable personas scraped from Prydwen + Contentful CDN images)
- Extend shared party components (`PartyViewConfig`, `PartyEditorModal`, `PartyCard`) with slot configuration to support heterogeneous slot types (fixed slots, filtered entity pickers)
- DB migration: purge existing P5X parties, expand slot range to 1–6 with member type discriminator, rename `thief_id` → `entity_id`
- Update P5X party service layer for new column mapping
- Update P5X `PartiesTab` to provide slot config with Wonder fixed + persona slots + thief slots
- Update data pipeline script to scrape persona catalog

## Capabilities

### New Capabilities

- `p5x-persona-catalog`: Static catalog of ~149 equippable personas for Wonder. Fields: id, name, rarity, role (job), element, imageUrl (Contentful CDN). Generated by update script, never edited manually.

### Modified Capabilities

- `shared-parties`: Extend `PartyViewConfig` with optional `slots` array enabling per-slot configuration (fixed display, entity filtering, custom labels). Default behavior (4 uniform slots) unchanged for existing games.
- `p5x-thief-catalog`: No catalog change, but party integration now treats thieves as one entity type in a union alongside personas.

## Non-Goals

- Persona tracking in roster (personas are only relevant inside party composition, not individually "owned")
- Wonder as a trackable roster entity (Wonder is implicit, always present)
- Changing any other game's party behavior (backward-compatible extension)
- Persona images from the game client (Contentful CDN source only)

## Slot Layout

```
Party structure (7 logical slots):
┌───────────────────────────────────────────┐
│ Slot 0: Wonder (FIXED — never in DB)      │
│ Slots 1–3: Persona picks (from catalog)   │
│ Slots 4–6: Phantom Thief picks (from roster) │
└───────────────────────────────────────────┘
```

Wonder (slot 0) is display-only, never persisted. DB stores slots 1–6 only.

## Migration Strategy

Destructive migration (user-approved): purge all existing P5X parties and party members, then alter schema. No data preservation needed.

```sql
DELETE FROM p5x_party_members;
DELETE FROM p5x_parties;
ALTER TABLE p5x_party_members DROP CONSTRAINT p5x_party_members_slot_index_check;
ALTER TABLE p5x_party_members ADD CONSTRAINT p5x_party_members_slot_index_check
  CHECK (slot_index >= 1 AND slot_index <= 6);
ALTER TABLE p5x_party_members ADD COLUMN member_type TEXT NOT NULL DEFAULT 'thief'
  CHECK (member_type IN ('thief', 'persona'));
ALTER TABLE p5x_party_members RENAME COLUMN thief_id TO entity_id;
```

## Open Risks

- Contentful CDN URLs are opaque (asset ID + hash per persona). If Prydwen re-uploads images, URLs break. Mitigation: upload to ImageKit like thieves, store local paths.
- HTML scraping for image URLs is fragile. Mitigation: the update script can fall back to placeholder if scrape fails for a given persona.
- `member_type` column is denormalized (derivable from slot_index range). Kept for query clarity and future-proofing if slot semantics shift.
