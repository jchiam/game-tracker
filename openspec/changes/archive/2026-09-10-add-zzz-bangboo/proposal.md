## Why

ZZZ parties field three agents plus one Bangboo — an off-field companion picked per squad, not per agent. The tracker's ZZZ parties currently stop at the three agent slots, so a saved party cannot record which Bangboo it runs. This is Phase 4 of the phased ZZZ delivery (roster/parties → Drive Discs → W-Engines → Bangboo), and the last planned ZZZ phase.

## What Changes

- New static Bangboo catalog (`src/data/zenless-zone-zero/bangboos.ts`): 38 Bangboos with name, rarity (S/A where known), and icon. Generated by `scripts/update-zzz-data.mjs` from a **new data source** — the HoyoLab wiki API (`sg-wiki-api.hoyolab.com`, Bangboo menu) — because the Enka store has no bangboo file and Dimbreath's mirror now obfuscates config filenames (verified 2026-08-17). Icons uploaded to ImageKit under `/zenless_zone_zero/bangboos`.
- One Bangboo pick per party: additive nullable `bangboo_id` column on `zzz_parties` (no member-row changes), surfaced through the party persistence `extras` seam.
- New shared **Companion Slot** seam on `PartyViewConfig`: an optional party-level single pick sourced from a separate catalog (not the roster), rendered as one extra slot in the party editor and one avatar tile on the party card. Games that omit it are byte-for-byte unchanged.
- ZZZ `PartiesTab` wires the seam: "Bangboo" slot in the editor with searchable picker, Bangboo tile on the party card.
- No tracking or investment fields — catalog + party slot only. No scoring impact.

## Capabilities

### New Capabilities

- `zzz-bangboo-catalog`: the static Bangboo catalog — entry shape, rarity handling, ordering, and the ImageKit icon resolver.

### Modified Capabilities

- `shared-parties`: new Companion Slot requirement — optional `PartyViewConfig` companion configuration drives an extra editor slot and card tile backed by a party-level column instead of a member row; absent config preserves existing behaviour for all games.
- `zzz-data-pipeline`: update script gains a Bangboo generation section fetching from the HoyoLab wiki API (new source alongside the Enka store), with `--reupload-bangboos` support.

## Impact

- **DB**: migration adding `bangboo_id TEXT` (nullable) to `zzz_parties`. Forward-only, permissive — existing rows and old app code unaffected.
- **Shared code**: `src/types.ts` (`Party.companionId`), `src/components/parties/` (PartiesView config type, PartyEditorModal, PartyCard, stories), `src/styles/party.css` / `PartyEditorModal.css` (minor slot styling).
- **ZZZ code**: `partyService.ts` (extras mapping), `PartiesTab.tsx` (companion config), `src/lib/imagekit.ts` (`getZzzBangbooIconUrl`).
- **Pipeline**: `scripts/update-zzz-data.mjs` new fetch/map/emit section + reupload flag; the HoyoLab wiki API needs POST requests, which the shared `fetchJSON` helper may need to support.
- **No CSP change**: wiki images are fetched at script time and served from ImageKit, never by the client.
