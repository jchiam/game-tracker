## Context

See proposal.md — Why. Current state: ZZZ parties render through the shared `PartiesView` with three uniform agent slots (`PartyViewConfig.slots` indices 0–2); `zzz_parties` carries `tier`/`is_favorited` extras via `createPartyPersistence`'s `extraSelect`/`extraFromRow`/`extraToRow` seam; `zzz_party_members` CHECKs `slot_index` 0–2. The Bangboo is party-level in game — one companion per squad, not one per agent — and comes from a catalog the tracker does not roster.

Data-source constraint (verified 2026-08-17): the Enka store (`store/zzz/`) has no Bangboo file; Dimbreath's `ZenlessData` mirror now obfuscates `FileCfg` filenames to numeric hashes (unusable without a hash map); Hakush.in remains dead (NXDOMAIN). The HoyoLab wiki API works unauthenticated with browser-like headers (`Origin`/`Referer: wiki.hoyolab.com`, `X-Rpc-Wiki_app: zzz`, `x-rpc-language: en-us`): menu tree pins **menu_id 15 = Bangboo** (under "Bangboo Database"), `get_entry_page_list` is a POST returning `{name, entry_page_id, icon_url, filter_values.bangboo_rarity}` — 38 entries today, `page_size` capped at 30 so pagination is required. Rarity tagging is incomplete (e.g. Booltergeist untagged even on its detail page).

## Goals / Non-Goals

**Goals:**

- One Bangboo per ZZZ party: nullable `bangboo_id` column on `zzz_parties`, picked in the party editor, shown on the party card.
- A generic, config-driven **companion slot** seam on the shared `PartiesView` — domain-neutral, so a future game with a party-level companion reuses it.
- Bangboo catalog + icons generated by the existing update script from the HoyoLab wiki API.

**Non-Goals:**

- No Bangboo tracking, investment fields, levels, or roster cards.
- No scoring impact — `zzzBuildScore.ts` and `discScoring.ts` untouched.
- No member-row/slot-CHECK changes on `zzz_party_members`.
- No companion adoption by other games in this change (seam only).

## Decisions

**D1 — Party-level column, not a fourth member slot.** `bangboo_id TEXT` (nullable) on `zzz_parties`, mapped through the existing `extraSelect`/`extraFromRow`/`extraToRow` seam like `tier`. Alternative — a member row at slot 3 with an entity-type discriminator (the P5X Navigator pattern) — rejected: member rows reference roster entities and the P5X pattern exists to partition one roster across typed slots; the Bangboo is catalog-only, and a tagged-union entity array plus `member_type` denormalization is heavy machinery for a single optional pick. The column also matches the in-game model (squad attribute, not a squad member).

**D2 — Generic `companionSlot` seam on `PartyViewConfig`, ZZZ wiring in `PartiesTab`.** New optional config: `companionSlot?: { label: string; entities: PartyEntity[]; resolveSlotImage; resolveListImage; searchPlaceholder? }`. `Party` gains `companionId?: string | null` (shared type, optional — same pattern as `tier`). The editor keeps one picker; `activeSlot` widens from `number | null` to `number | 'companion' | null`, and when the companion slot is active the picker sources `companionSlot.entities` with a name-only Fuse search (config `searchKeys` describe roster entity fields and don't apply). `handleSave` spreads `{ companionId }` only when the config declares the slot — games without it send identical payloads to today. Alternative — a ZZZ-only fork of the editor — rejected: per-game `PartiesTab` files are thin config adapters by convention; forking the editor breaks the Party View seam.

**D3 — Card tile always rendered when configured, empty placeholder when unset.** The card appends a labelled companion tile after the member slots, reusing `.slot-avatar` (avatar + `.char-name-small` when set, `.empty-plus` when unset) — consistent with empty member slots, and the empty tile advertises the affordance. In the editor the companion renders as one extra `builder-slot` in its own labelled group panel ("Bangboo"), visually separated from the agent trio.

**D4 — Wiki `entry_page_id` as catalog id.** Stable, survives renames, and is the natural key for the icon asset path (`/assets/zenless-zone-zero/bangboos/{id}.webp` locally, `zenless_zone_zero/bangboos/{id}.png` on ImageKit). Alternative — slugified name — rejected: renames would orphan saved `bangboo_id` values.

**D5 — Nullable rarity, no hand-curated override file.** `rarity: 'S' | 'A' | null` straight from the wiki's `bangboo_rarity` filter; untagged entries stay `null` and the picker simply shows no rarity badge. Alternative — a hand-curated override map (the `disc_suit_short_names.ts` precedent) — deferred: rarity is a display nicety on a picker row, not load-bearing; add overrides only if the gaps grow annoying.

**D6 — Pipeline: new fetch+map+emit section; `fetchJSON` learns POST.** The Bangboo section follows the suit/engine shape (loadExisting → fetch → map → `ensureAsset` loop → generate + diff), with `--reupload-bangboos` via `parseReuploadFlags`. The wiki list endpoint is a POST with required headers, so the shared `fetchJSON` gains an optional `init` (RequestInit) parameter — additive, existing GET callers unchanged. Pagination loops `page_num` until the reported `total` is collected. Icons come from the wiki's `icon_url` (hoyoverse CDN) at script time only — no client CSP change.

**D7 — Icon resolver `getZzzBangbooIconUrl`, plain `tr:w-128`.** Wiki bangboo icons are square renders on transparent canvas — same treatment as disc-suit and W-Engine icons, no crop chain. Per Jonathan's standing preference, stored assets are untouched originals; all sizing is on-the-fly.

## Risks / Trade-offs

- [Wiki API is unofficial-surface and could change or start rejecting scripted calls] → Isolated to one fetch closure in the update script; the weekly workflow fails loudly and the committed catalog keeps working. Headers mimic the public wiki site; volume is ~2 requests/week.
- [`page_size` cap or `total` semantics change] → Pagination loop guards on both `total` and an empty-page break to avoid infinite loops.
- [Rarity gaps in wiki tagging] → Accepted (D5); `null` renders as no badge.
- [Widening `activeSlot` to `number | 'companion'` touches shared editor logic used by all six games] → All companion branches are gated on `config.companionSlot`; existing PartiesView tests plus a no-config regression assertion cover the unchanged path.
- [`Party.companionId` optional on the shared type tempts other games' extras to drift] → Same accepted trade-off as `tier`/`isFavorited`; convention documented in the seam's JSDoc.

3. Jonathan applies the migration to live Supabase before merge-to-deploy (established phase ritual).
4. Rollback: revert the app changes; the column can stay (nullable, ignored by old code) or be dropped after confirming no non-null values worth keeping.
