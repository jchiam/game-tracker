## ADDED Requirements

### Requirement: Light Cone catalog data file

The system SHALL maintain a generated catalog of HSR Light Cones in `src/data/honkai-star-rail/light_cones.ts`, exporting a `LightCone` interface and a `const ALL_LIGHT_CONES: LightCone[]`. Each entry SHALL have the fields: `id` (string — the stable StarRailRes light-cone id), `name` (string, display name), `rarity` (integer 3–5), `path` (string, display name of the cone's Path), and `imageUrl` (local asset path `/assets/honkai-star-rail/light-cones/{id}.webp`). The file SHALL carry the standard generated-file banner and SHALL never be edited by hand. Entries SHALL be sorted by rarity descending, then name ascending.

#### Scenario: Catalog accessible at runtime

- **WHEN** any component imports `ALL_LIGHT_CONES` from `@/data/honkai-star-rail/light_cones`
- **THEN** the full array of `LightCone` entries is available with `id`, `name`, `rarity`, `path`, and `imageUrl` fields

#### Scenario: All equippable rarities included

- **WHEN** the catalog is generated
- **THEN** it contains Light Cones of rarity 3, 4, and 5 (3★ cones are legitimate equips, unlike 3★ characters)

### Requirement: Catalog generated by the HSR update script

`scripts/update-hsr-data.mjs` SHALL fetch `index_new/en/light_cones.json` from StarRailRes alongside its existing fetches and regenerate `light_cones.ts` on every run. The script SHALL diff the new catalog against the existing file and report added/removed entries, consistent with its character and relic-set handling.

#### Scenario: Weekly workflow refreshes the catalog

- **WHEN** the HSR data workflow runs `update-hsr-data.mjs`
- **THEN** `light_cones.ts` is regenerated from the latest StarRailRes data and any catalog changes appear in the auto-created PR diff

### Requirement: Light Cone path uses the shared path vocabulary

Each cone's `path` SHALL be resolved through the same StarRailRes `paths.json` id-to-display-name map used for character paths, so that `LightCone.path` exactly string-matches the value space of `Character.path`. This exact-match contract is the join key for the path-filtered cone picker.

#### Scenario: Path strings cannot drift

- **WHEN** the update script generates both `characters.ts` and `light_cones.ts`
- **THEN** both `path` fields are produced from the single shared path map, with no casing or spelling divergence

#### Scenario: Picker resolves equippable cones by exact match

- **WHEN** the character card filters `ALL_LIGHT_CONES` for a character
- **THEN** the equippable set is exactly `ALL_LIGHT_CONES.filter(lc => lc.path === character.path)`

### Requirement: Light Cone images on ImageKit

The update script SHALL download each cone's icon from StarRailRes to `public/assets/honkai-star-rail/light-cones/{id}.webp` and upload it to ImageKit via the shared `ensureAsset` helper, skipping assets that already exist unless a `--reupload-light-cones` flag is passed. Catalog entries reference the local asset path; runtime resolution to CDN URLs goes through `src/lib/imagekit.ts`.

#### Scenario: Idempotent image upload

- **WHEN** the script runs and a cone's image already exists on ImageKit
- **THEN** the asset is skipped (result `'skipped'`) unless `--reupload-light-cones` is passed

#### Scenario: New cone gets an image

- **WHEN** StarRailRes adds a new Light Cone
- **THEN** the next script run downloads its icon, uploads it to ImageKit, and the new catalog entry references `/assets/honkai-star-rail/light-cones/{id}.webp`
