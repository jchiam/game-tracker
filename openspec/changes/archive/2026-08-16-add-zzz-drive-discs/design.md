# Design — Add ZZZ Drive Discs (Phase 2)

## Context

Phase 1 (`2026-08-16-add-zzz-phase-1-roster-parties`, PR #48) shipped the ZZZ roster, parties, and agent catalog. The service (`agentService.ts`) has no `extras` seam yet, the hook uses only `makeFieldUpdater` paths, and `AgentCard` has an empty `summaryLine` and no `headerExtra` — all deliberate Phase 2 landing points. The HSR relic implementation is the reference pattern; N2E cartridges and P5X revelations are simpler variants of the same machinery (shared `createRosterPersistence` extras seam, `savePreferenceRows`, `chainToRows`/`rowsToChain`, `EquipmentEditorShell`, `createEquipmentScore`).

ZZZ Drive Disc domain facts driving the model:

- 6 disc slots per agent, numbered 1–6.
- Slots 1–3 have fixed main stats: slot 1 = HP, slot 2 = ATK, slot 3 = DEF.
- Slots 4–6 have variable main stats (slot 4: crit/anomaly-proficiency group; slot 5: PEN ratio + element DMG bonuses; slot 6: impact/energy/anomaly-mastery group).
- Substats come from a single 10-stat pool; each disc holds up to 4.
- Set bonuses are 2-piece and 4-piece from a **single suit pool** (~30 suits) — no cavern/planar split. A typical target build is "4pc suit X + 2pc suit Y".
- Enka `store/zzz/equipments.json` provides `Suits` (icon path, locs name key, 2pc bonus props) — enough for a catalog of id/name/icon.

## Goals / Non-Goals

**Goals:**

- Per-agent equipped-disc tracking (suit + main stat + substat types per slot).
- Per-agent target build: 4pc suit, 2pc suit, main-stat preference chains for slots 4–6, global substat chain, comments.
- Equipment-match score (0–100 + grade) on the agent card, replaying the HSR scoring shape via the shared factory.
- Disc suit catalog generated by the existing update script, icons on ImageKit.

**Non-Goals:**

- W-Engine equip/preferences/score blend — Phase 3.
- Bangboo — Phase 4 (KIV).
- Substat numeric values — HSR dropped them (migration `20260710000004`); ZZZ never adds them.
- Disc level/rarity tracking — the tracker records stat shapes, not roll quality.
- 4pc bonus text in the catalog — Enka only carries 2pc props; the catalog needs only id/name/icon.

## Decisions

### D1 — Numeric slot model, fixed mains encoded in the data module

`ZzzDiscSlot = 1 | 2 | 3 | 4 | 5 | 6`. DB column `slot INTEGER CHECK (slot BETWEEN 1 AND 6)`. Fixed mains for slots 1–3 and the variable-main pools for slots 4–6 live **once** in `src/data/zenless-zone-zero/discs.ts` (`ZZZ_DISC_MAIN_STATS`, `ZZZ_DISC_SUB_STATS`), imported by both the editor and the scorer.

_Why:_ ZZZ slots are canonically numbered (no community slot names), and HSR's duplicated main-stat maps (`MAIN_STATS` in `relics.ts` unused; `VALID_MAIN_STATS` re-declared in `RelicEditorModal.tsx`; `ALL_SUB_STATS` re-declared in `relicScoring.ts`) is a known wart we're explicitly not replaying.

_Alternative considered:_ named slots (`'disc1'`…) — adds a naming layer with no consumer.

### D2 — Suit picks as parent columns, chains in one category table

- `zzz_tracked_agents` gains `disc_suit_4_id TEXT`, `disc_suit_2_id TEXT`, `disc_comments TEXT` (additive `ALTER TABLE`).
- One preference table `zzz_disc_preferences`: `tracked_agent_id FK`, `category TEXT CHECK IN ('slot4_main','slot5_main','slot6_main','sub_stats')`, `stat`, `operator_to_next CHECK IN ('>','>=','OR') OR NULL`, `order_index`.
- `saveDiscPreferences` = one `savePreferenceRows` call: `deleteFrom: [zzz_disc_preferences]`, `parentUpdate: { disc_suit_4_id, disc_suit_2_id, disc_comments }`, one insert set.

_Why:_ single-select suit picks are scalar → parent columns (HSR precedent: `relic_set_id`/`planar_set_id`). Chains use the newest house pattern (P5X `p5x_revelation_preferences` single table + category enum) — one table, one delete, one insert, instead of HSR's two tables. Minimizes the non-atomic delete/reinsert surface documented in Known Limitations.

_Alternative considered:_ HSR's two-table shape (`_main_stats` with slot column + `_sub_stats`) — more moving parts, no benefit.

### D3 — Equipped discs replay the HSR two-table shape

`zzz_equipped_discs` (`tracked_agent_id FK CASCADE`, `slot`, `suit_id TEXT`, `main_stat TEXT`, `UNIQUE(tracked_agent_id, slot)`) + `zzz_disc_substats` (`disc_id FK CASCADE`, `stat_type TEXT NOT NULL`). `upsertDisc` = upsert on `(tracked_agent_id, slot)` then delete+reinsert substats — same as `upsertRelic`.

_Why:_ proven shape; the substat list is genuinely variable-length. RLS: four named policies per table, child via `EXISTS` on parent, grandchild via two-level `EXISTS … JOIN` — matching the `20260816000000` house style.

### D4 — Removal writes `null`, not an empty-disc object

`removeDiscData` sets the optimistic slot to `null` (matching what a reload yields after row deletion). HSR's `emptyRelic` sentinel makes an in-session emptied slot score differently from the same slot after refresh; ZZZ does not inherit that asymmetry. The scorer therefore only ever sees `null` or a populated disc.

### D5 — Scoring: shared factory, greedy 4pc/2pc set term

`src/utils/discScoring.ts` = `createEquipmentScore<ZzzTrackedAgent>` adapter:

- Stat vocabulary map (`ZZZ_STAT_SHAPES`) for `makeStatMatcher`: HP/ATK/DEF flat+percent pairs, CRIT Rate/DMG cross-match, PEN vs PEN Ratio as a flat/percent pair; element DMG bonuses and the slot-6 utility stats are exact-match only.
- `slots`: 6 entries. Slots 1–3 → `mainMatch = 1.0` (fixed). Slots 4–6 → empty chain = 1.0 (don't-care), chain set + no equipped main = 0, else `bestMatch`.
- `setTerm`: greedy piece assignment — count equipped discs matching `discSuit4Id`, capped at 4, feeding a `/4` term; count matching `discSuit2Id`, capped at 2, feeding a `/2` term; when both picks are the same suit, pieces beyond the first 4 spill into the 2pc count. Weights 0.67 / 0.33 (HSR's cavern/planar split, same rationale: 4pc dominates the build identity).
- Grade + badge via shared `getScoreGrade` / `ScoreBadge`; `-1` sentinel hides the badge.

_Why greedy spill:_ equipping 6 pieces of one suit is legal in game and should not score worse than 4+2 of two suits when the user targets that suit in both picks.

_Phase 3 seam:_ `AgentCard` renders the disc score directly this phase; Phase 3 wraps it in a blend (HSR `buildScore.ts` shape) without touching `discScoring.ts`.

### D6 — Catalog generation and icons

`update-zzz-data.mjs` gains a discs section in the reserved slot: fetch `equipments.json`, iterate `Suits`, resolve names via existing locs helper, `ensureAsset` each icon from `https://enka.network${suit.Icon}` to ImageKit path `/assets/zenless-zone-zero/disc-suits/{suitId}.png`, emit generated `disc_suits.ts` (`ZzzDiscSuit { id, name, icon }`, alphabetical, `generatedHeader` banner, `jsStr` quoting for Prettier stability). `parseReuploadFlags(['agents','discs'])` adds `--reupload-discs`. Multi-catalog emission follows the `update-hsr-data.mjs` shape (parallel loadExisting/generate, one fetch block, one write block, per-catalog diff summary).

Hand-curated `disc_suit_short_names.ts` (suit id → one-word label) for the card digest line — mirroring HSR's `relic_short_names.ts`, never written by the script. New suits fall back to the full name until curated.

`src/lib/imagekit.ts` gains `getZzzDiscSuitIconUrl` — simple width transform (icons are already square art), no crop chain.

### D7 — Hook and UI wiring

- `useAgents`: pull `setTrackedEntities` / `trackedRef` / `queueAction` from `useRoster`; add `saveDiscData` (key `${dbId}-${slot}`), `removeDiscData` (key `${dbId}-${slot}-delete`), `saveDiscPreferences` (key `${dbId}-discprefs`) — per-slot key namespacing because `queueAction` is latest-wins per key. `getFilteredRoster` gains `'SCORE'` sort with a page-supplied `scoreFor` callback (HSR shape).
- `ZzzPage`: `editingDisc: { agentId, anchorSlot } | null` state; conditional `DiscEditorModal` mount (HSR `HsrPage.tsx` seam).
- `DiscEditorModal` over `EquipmentEditorShell`: Equip tab = 6 `.equip-slot-card` blocks (suit `Select` over one pool — no family filtering; main-stat `Select` for slots 4–6, read-only fixed stat for 1–3; `SubStatList`; progressive `is-gated` gating; main-stat pruned from substats on save; `useScrollAnchor` on `anchorSlot`). Preferences tab = 4pc + 2pc suit `Select`s, `PreferenceChain` ×3 (slots 4–6), global substat `PreferenceChain`, `BuildComments`; whole-object `onUpdateBuildPreferences`.
- `AgentCard`: `.card-section-group` "Drive Discs" with `.equip-slot-grid` of 6 cells (suit icon or fallback glyph, click opens editor at slot); suit digest `summaryLine` from short names + counts (em-dash placeholder when empty); Target Build readout (`.build-prefs-display` grid: suit badges row, `PreferenceChainReadout` ×3 + Subs, comments row); `headerExtra={<ScoreBadge …/>}` + `temperScore`.

## Risks / Trade-offs

- [Non-atomic preference save] — inherited, documented Known Limitation; single `savePreferenceRows` call site keeps the future RPC fix one-shot. Mitigated by `usePendingSaves` retry toast.
- [Non-atomic substat reinsert in `upsertDisc`] — same shape as HSR `upsertRelic`; accepted for parity.
- [Main-stat pools are hand-maintained game knowledge] — new patch stats (new element, new slot-6 stat) require a manual edit to `discs.ts`. Same exposure as HSR/N2E; catalogs of suits are generated, stat pools are not derivable from Enka.
- [Same-suit 4pc+2pc spill logic is bespoke] — unit-test the three regimes (distinct suits, same suit ≤4 pieces, same suit 5–6 pieces) explicitly.
- [Enka icon paths could drift] — `ensureAsset` failure lists missing icons without failing the run; card renders fallback glyph.

## Migration Plan

1. Migration file `20260817000000_add_zzz_disc_tables.sql` (additive: two new tables + one pref table + three `ALTER TABLE zzz_tracked_agents ADD COLUMN`). Apply to live Supabase after merge (Jonathan applies manually, as in Phase 1).
2. App code is null-safe before the migration applies: `extras.selectFragment` only ships in the same release, and absent rows map to empty discs/prefs.
3. Rollback = drop the three new tables + three columns; no existing data touched.
