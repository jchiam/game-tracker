## Context

P5X tracks Thief investment across level, awareness, weapon, mindscape, and skills. Revelation Cards are the remaining major investment axis — a 5-slot gear system analogous to HSR relics. HSR relics are already tracked per-slot with a separate `hsr_equipped_relics` table + `hsr_relic_substats` join table.

P5X revelations have a simpler stat model (no enhancement level, no roll-value tracking beyond the 4 substats), which allows a lighter DB schema while preserving full per-slot visibility.

## Goals / Non-Goals

**Goals:**

- Track per-Thief revelation setup: which set in each slot, what main stat, what substats
- Track build preferences: target sets and stat priorities for farming guidance
- Match HSR-level visibility in the card UI (summary chip + full edit section)
- Reuse existing shared patterns (savePreferenceRows, Select, SubStatList, PreferenceChain)

**Non-Goals:**

- Card enhancement levels (1–15) — adds complexity without actionable signal; can add later
- Per-substat roll quality tracking (min/max roll) — deferred; the value number captures this implicitly
- Revelation score algorithm (like hsr-relic-scoring) — deferred to a follow-up change
- Automated set recommendation engine

## Decisions

### D1: JSONB substats vs separate table

**Decision:** Store substats as a JSONB array column on the revelation cards table, not a separate join table.

**Rationale:** HSR uses a join table (`hsr_relic_substats`) because it was built first and followed normalized form. In practice, substats are always read/written as a unit with their parent card — never queried independently. JSONB avoids the extra table, simplifies upsert to a single row operation, and eliminates the non-atomic delete-then-reinsert for substats.

**Alternative:** Separate `p5x_revelation_substats` table (like HSR). Rejected — adds complexity with no query benefit for this use case.

### D2: Single cards table vs inline columns

**Decision:** Separate `p5x_revelation_cards` table with one row per equipped slot, rather than 5×N columns on the tracked_thieves table.

**Rationale:** 5 slots × (set + main_stat + substats) = 15+ columns inlined would bloat the thief table. A separate table keeps the main table lean, allows nullable slots naturally (missing row = empty slot), and the UNIQUE(thief_row_id, slot) constraint enforces one-card-per-slot.

**Alternative:** Inline all as JSONB on tracked_thieves (e.g. `revelations JSONB`). Rejected — harder to partially update one slot without reading the whole blob, and RLS on the parent row already covers access.

### D3: Preferences in same table as HSR/N2E pattern

**Decision:** Use a `p5x_revelation_preferences` table following the same `savePreferenceRows` pattern (category + stat + operator + order_index rows). Set preferences stored as single rows with stat = set ID.

**Rationale:** Reuses the proven shared helper. Identical pattern to HSR `buildPreferences` and N2E `cartridgePreferences`. One implementation path, one known caveat (non-atomic saves).

### D4: Catalog in static data file, not DB

**Decision:** Revelation set catalog (names, effects) lives in `src/data/persona-5-phantom-x/revelations.ts` as static arrays, generated by the update script.

**Rationale:** Set catalog rarely changes (game patches). Static data avoids a DB table, keeps the data layer pattern consistent with other catalogs (ALL_THIEVES, ALL_PERSONAS, ALL_RELICS). The update script can scrape Prydwen for new sets.

### D5: UI placement — edit section ordering

**Decision:** Revelations edit section placed between Weapon and Mindscape, matching the summary chip order: Level → Weapon → Revelations → Mindscape → Skills.

**Rationale:** Investment depth ordering — revelations are the mid-to-late game system (unlocks at Lv35), sandwiched between weapon (early investment) and mindscape/skills (endgame completion toggles).

## Risks / Trade-offs

- **JSONB migration to typed columns**: If we later need to query substats across all thieves (e.g. "who has Crit Rate% sub?"), JSONB is queryable via `->>` but slower than a normalized table. Acceptable for a personal tracker's data volume. → Mitigation: can add a GIN index on `sub_stats` if needed.

- **Non-atomic preference saves**: Same caveat as HSR/N2E — delete-then-reinsert for preference rows. → Mitigation: same as existing — `usePendingSaves` retry + error toast. Future fix (plpgsql RPC) has one call site in `savePreferenceRows`.

- **Card edit section length**: 5 slot editors + preferences could make the edit body very tall. → Mitigation: collapsible per-slot accordions or a tabbed sub-view within the edit section. Design during implementation.

- **Prydwen data freshness**: New sets added in game patches need a script update. → Mitigation: same pattern as all other catalogs — weekly GitHub Actions workflow + manual dispatch.

## Open Questions

- Should the revelation edit section use inline per-slot editors (vertically stacked) or a tabbed approach (one slot visible at a time)? Defer to implementation — try inline first, switch to tabs if too tall.
